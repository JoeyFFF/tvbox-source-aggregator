# 频道固化框架与源健康度：实测反馈与设计提案

> 2026-11-09。基于一份真实公开源（1093 频道 / 4628 条源）的实机使用反馈，
> 附两组可复现的实测数据，以及由此推导的结构性改造提案。

## 一、现象

频道测速已开启（多采样取中位数、TTL 6h、按延迟升序排序），理论上每个频道的首选源就是当前最快的。
但电视端（直播壳设「5 秒无响应自动换源」）实际切台时，经常要等一次超时才进得去。

测速没有失效，**是测速的"探测深度"不够**。

## 二、实测

### 2.1 排第一的源，34% 播不了

取输出里前 80 个频道，只验证每个频道**当前排第一**的源，做两级判定：

1. 拉播放列表（现有测速就停在这一步）
2. 顺着列表拉**第一个分片**（ts / fmp4），看能否真出数据

```
playable          53   66%     列表 + 分片都正常
segment_fail      18   23%     列表 200 且含 #EXTM3U，但分片 404 / 超时
playlist_fail      5    6%     列表本身 403
variant_fail       4    5%     主列表里的子列表拉不到
───────────────────────────────
实际不可播         27   34%
```

`segment_fail` 是关键一类：**列表由 CDN 静态返回，分片却指向另一台已失效的源站**。
这类源在现有探测里会被判成"可用且最快"，稳坐第一位。
实测 53 个可播源中有 11 个的分片域名与列表域名不同，说明 CDN 与源站分离是常态，这层差异必须测。

### 2.2 坏源排第一，好源就在第 2~3 位

```
首位不可播的频道            21
  后面 4 条内有可用源        11  (52%)
  前 5 条全废               10

可用源被埋到的位置：第 2 位 5 个 / 第 3 位 4 个 / 第 4 位 1 个 / 第 5 位 1 个
```

`CCTV4` 共 80 条源，可用源排第 **3**；`CCTV15` 共 75 条，可用源排第 **5**。
电视端为此要连续失败 1~2 次（5~10 秒）。

### 2.3 前三条源常在同一域名，会一起挂

```
342 个多源频道里，107 个（31%）前 3 条源域名完全相同
全局最集中的源域名：45.192.97.170（487 次）、38.75.136.137（127 次）
```

该域名一抖动，前三条一起失败，连试 3 次 = 15 秒。这与单条源质量无关，是排序缺少**多样性约束**。

## 三、根因

`src/core/channel-probe.ts` 的 `probeOnce()` 目前是：

| 协议 | 判定方式 | 速度口径 |
|---|---|---|
| m3u8 | 读首包 1KB，含 `#EXTM3U` 即通过 | 该次请求 TTFB |
| ts / flv / mp4 | 首包 4KB 内找 sync byte `0x47` | 同上 |
| 其他 | 能建连即算 `tcp` | 同上 |

四个盲区：

1. **只验清单，不验货物** —— 列表可达 ≠ 分片可播（实测 23% 卡在这里）。
2. **没有持续吞吐** —— TTFB 快不代表码率够；10ms 的源可能在 200KB 后卡死。
3. **排序无去相关** —— 纯按速度排，同域名多条源被挤到最前。
4. **没有运行时闭环** —— 客户端换源失败不会回流，坏源会占位到下一轮测速（6h）。

## 四、设计提案：从「每次重建」到「长期实体」

### 4.1 核心转变

现在每次聚合都从源 txt 重建频道树，频道只是**本次运行里的一个名字字符串**。
名字写法一变（`CCTV-1` → `CCTV1综合`），就是一个新频道，历史全部丢失，所以无法积累"这条源长期靠不靠得住"。

改成三层实体：

```
频道目录 (Registry)          长期存在，有稳定 id 与人工确认的别名
  └ 频道槽位 (Slot)          cctv-1 / 卫视-湖南 / ...
      └ 源档案 (Source)      一条 URL 的长期健康档案
          └ 健康记录 (Health) 每轮 L1/L2/L3 结果 + 时间序列
```

`channel_id` 稳定，才谈得上"健康监察"。

| 表 | 关键字段 |
|---|---|
| `channel_registry` | `id`(cctv-1)、`name`、`group`、`order`、`aliases[]`、`logo`、`enabled` |
| `channel_source` | `channel_id`、`url`、`source_name`、`host`、`protocol`、`first_seen`、`state` |
| `source_health` | `url`、`round`、`l1_ok`、`l2_ok`、`l3_kbps`、`jitter_ms`、`seg_ok_rate`、`consecutive_fail`、`last_ok_at` |

### 4.2 自动归入：把"判断"变成一次性知识

来源频道的名字五花八门，但归入 `channel_id` 可以做成分层判定，且**命中一次就固化**：

```
① 完全匹配 channel_id / 正式名        → 直接归入
② 别名表命中                         → 直接归入
③ 规则归一（央视编号 / 繁简 / 后缀剥离）→ 归入，记入待确认
④ 模糊匹配（编辑距离 ≤ 阈值）          → 归入，低置信度标记
⑤ 全不中                             → 「未识别队列」
```

`⑤` 是后台的一个列表：新出现的频道名集中在这里，人工点一次「归入 CCTV5+」，
写入别名表，**以后永不再判断**。这一步把运行时的模糊判断转成了一次性人工确认，
比每次聚合都跑一遍猜测稳定得多。

规则层可以直接复用现有的 `normalizeCctvName` / `TRAD_SIMP_MAP` / `SUFFIX_PATTERNS`。

**必须保留的逃生口**：固化框架最大的风险是"新频道进不来"。
所以 `⑤` 除了人工确认，还要有「N 天内未被确认则自动建新槽位」的策略，
否则源更新出的新频道会被静默吞掉。

### 4.3 健康度模型

```
availability = (近 N 轮成功次数 + 1) / (N + 2)        # 拉普拉斯平滑，新源不被打死
quality      = w1·availability + w2·norm(p50) + w3·norm(throughput) + w4·(1 - jitter_penalty)

硬门槛：l2 连续失败 ≥ 2 轮 → quarantined（保留在列表，但不参与优先排序）
排序：先按 availability 分桶（≥0.9 / 0.6~0.9 / <0.6），桶内按 quality 降序
去相关：前 3 名尽量来自不同 host（同 host 最多 1 条）
时间衰减：只用近 7 天数据，历史权重按半衰期衰减
```

关于「丢包」：HTTP 层拿不到 ICMP 丢包率。可用的代理指标是
**分片成功率 + RTT 抖动（MAD/median）**，两者一起能识别"连得上但质量差"的源。

### 4.4 探测分级（成本可控）

```
L1  列表可达            全量（现状）            ~1.6 万次
L2  首分片可取 4~8KB    仅 L1 通过者            ~1.1 万次（多数失败是秒级 404）
L3  3 个分片的吞吐/抖动  仅"候选前 N 名"         每频道 2~3 条
```

L2 的关键是**失败得快**：分片 404 通常 100ms 内返回，不会吃满 5 秒超时，
所以全量加 L2 的耗时增量远小于直觉。

**固化带来的额外收益**：频道固定后，每个频道只需保留 top N（比如 8 条）候选源，
测速规模可从 1.6 万降到 6~8 千，于是**深探测在经济上才成立**。
这两件事是互为前提的 —— 这也是我认为该一起做的原因。

### 4.5 源健康看板（可视化）

沿用现有分组/频道框架，新增一页：

```
┌─ 概览 ──────────────────────────────────────────────┐
│ 源 4628 · 可用 1093 · 隔离 312 · 平均切台成本 0.4 次 │
├─ 左：分组 → 频道 ────┬─ 右：该频道的源 ──────────────┤
│ 央视 (56)            │ # 源名      域名     状态  p50 │
│   CCTV1     ●  18ms  │ 1 南风直播  120.76… ● 18ms   │
│   CCTV2     ◐  210ms │ 2 游魂      39.165… ● 23ms   │
│   CCTV3     ○  隔离  │ 3 电视直播  118.19… ◐ 分片失败│
│ ...                  │ ...                          │
│                      │ 7 日延迟 sparkline           │
└──────────────────────┴──────────────────────────────┘
操作：置顶 / 禁用 / 隔离 / 「同域名只留 1 条」
解释：「为什么排第一」→ 展开分数构成（可用率 0.98 · p50 18ms · 抖动 4ms）
```

这个页面不只是"看"，它同时是**别名确认的唯一入口**（未识别队列也放在这里），
以及"人工干预"的出口：置顶/禁用写回 `channel_source`，下次排序叠加。

## 五、落地顺序

| 阶段 | 内容 | 收益 | 成本 |
|---|---|---|---|
| P0 | L2 分片探测 | 直接消灭 23% 的"列表可播但实际不可播" | 半天 |
| P1 | 域名去相关（前 3 名不同 host） | 消除 31% 的"连挂三次" | 十几行 |
| P2 | 源健康档案 + 分桶排序 | 抖动不再影响排序，长期优质源自然上浮 | 一天 |
| P3 | 频道目录 + 别名表 + 未识别队列 | 新源自动归入，不再重复判断 | 一天 |
| P4 | 健康看板 UI | 可视化监察与人工干预 | 一天 |

P0 + P1 就能解决绝大部分体感问题，且不需要改数据模型；
P2 往后才是结构性改造。

## 六、附：复现方法

判断"列表可播但分片不可播"的最简流程：

```
1. GET 播放列表 → 若含 #EXTM3U
2. 若有 #EXT-X-STREAM-INF（主列表）→ 取第一条子列表，再 GET 一层（最多 2 层）
3. 取第一个非 # 开头的行，按 base URL 解析成分片地址
4. GET 该分片，读 4~8KB
5. 判定：HTTP 200 且字节数 ≥ 2KB 视为可播
```

80 个频道采样、6 秒超时、12 并发，40 秒可跑完。
